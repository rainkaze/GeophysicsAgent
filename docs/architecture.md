# 架构与数据流

## 1. 分层

```
┌─────────────────────────────────────────────────────────┐
│ api/          HTTP 协议层：路由、依赖注入、错误映射        │
├─────────────────────────────────────────────────────────┤
│ agent/        编排层：抽取 → 检索 → 评估 → 规划 → 校验 → 渲染 │
├─────────────────────────────────────────────────────────┤
│ analysis/     确定性计算层：方法元数据、物理关系、评估器    │
│ knowledge/    检索层：BM25 索引与课程证据                  │
├─────────────────────────────────────────────────────────┤
│ domain/       领域模型：枚举、条件、评估结果、方案、DTO     │
│ core/         配置                                       │
└─────────────────────────────────────────────────────────┘
```

依赖方向自上而下，**没有任何模块反向依赖 `agent`**。`analysis` 与 `knowledge`
完全不调用大模型，因此可以单独做单元测试与复现。

| 模块 | 职责 | 是否调用模型 |
|---|---|---|
| `api/routes.py` | 路由、依赖注入、HTTP 错误映射 | 否 |
| `agent/runner.py` | 主循环：编排各阶段、记录轨迹、组装响应 | 是（转发） |
| `agent/intake.py` | 规则抽取场地条件、生成追问 | 否 |
| `agent/llm.py` | 结构化 JSON 输出、重试、用量统计 | 是 |
| `agent/planner.py` | 生成草案、修复草案、规则兜底方案 | 是 / 否 |
| `agent/verifier.py` | 14 条确定性校验规则 | 否 |
| `agent/renderer.py` | 由结构化方案渲染 Markdown | 否 |
| `agent/session_store.py` | 会话条件记忆（TTL + LRU） | 否 |
| `agent/trace.py` | 执行轨迹记录 | 否 |
| `analysis/catalog.py` | 方法元数据、干扰严重度 | 否 |

## 3. 一次请求的数据流

1. **intake**：`extract_conditions` 用规则把自然语言解析成 `SiteConditions`；
   与上一轮会话条件合并。
2. **澄清判断**：缺 `target / medium / depth` 任一 → 直接返回 `mode=clarification`，
   不调用模型、不猜测。
3. **retrieve**：BM25 检索课程知识，输出 `Evidence[]` 与相关性等级
   （strong / weak / empty）。
4. **assess**：`calculator.assess` 对六种方法逐一给出最大深度、余量、分辨率、
   采集参数、限制与适用性，并选出推荐主方法；`design.build_design` 估算测线与成本。
5. **plan**：模型读取评估表，输出 `PlanDraft`（只包含方法角色与定性理由）。
6. **verify → repair**：14 条规则校验；出现 `error` 就把问题回灌模型重写（≤N 次）。
7. **design 重算**：按最终主方法重新计算外业布置与工作量。
8. **render**：由**已校验的结构化方案**渲染 Markdown 正文，数值与表格同源。
9. **remember**：把条件写回会话，供追问使用。

## 4. 关键设计决策

### 4.1 数值由代码算，模型只做决策

早期版本让模型直接写"电极距 2 m、排列长 90 m"，无法核对也无法复现。
现在所有数值来自 `analysis/` 的确定性计算，模型只选择"谁是主方法、理由是什么"。
模型若引用不存在的数值，会在提示词层面被禁止，在渲染层面也无从体现——正文由代码拼装。

### 4.2 条件抽取用规则，不用模型

字段有限、模式稳定（埋深范围、介质、干扰），规则可解释、零成本、零延迟、可单测。
规则漏抽只影响"是否追问"，不会产生错误数值。

### 4.3 工具由运行时编排，而非模型自由调用

模型不决定"要不要查参数表"，而是每次都由 `calculator` 全量评估六种方法后再让它选择。
理由：勘察方案必须**穷举比较**，让模型自由决定调用会造成漏评；同时保证同一输入的可复现性。

### 4.4 校验器是硬约束

`verifier.py` 用纯规则检查模型输出：主方法是否深度可行、是否被判不适用、
受限方法是否给出应对、验证措施是否可执行、是否超出预算档位……
这是"模型可以礼貌地无视工具结论"这一问题的制度性解法。

### 4.5 失败必须可降级

模型未配置、超时、输出不合法、修复后仍不通过——四种情况都会回退到
`planner.fallback_plan` 的规则方案，并在响应中标记 `mode=degraded`。
**演示现场即使断网或模型故障，系统仍能给出物理上成立的方案。**

## 5. 信任边界

- 浏览器不接触模型 Key，配置只从后端本机 `.env` 读取；
- 知识命中 ≠ 已核验：响应携带 `verification_status` 与 `evidence_quality`；
- 所有深度、分辨率、成本均为教学用经验估值，响应固定附带免责声明；
- 会话状态只存在进程内存，重启即清空。

## 6. 扩展点

| 需求 | 改动位置 |
|---|---|
| 新增物探方法 | `domain/enums.py` 加枚举 → `analysis/tables.py` 补深度/适用性 → `analysis/physics.py` 补采集参数 |
| 新增探测目标 | `domain/enums.py` + `analysis/tables.py`（别名、对比、适用性行） |
| 调整判定策略 | `analysis/calculator.py` 的阈值常量与判定顺序 |
| 新增校验规则 | `agent/verifier.py` 加一条 `Violation`，并在 `tests/test_verifier.py` 补用例 |
| 更换模型供应商 | `agent/llm.py`（任何兼容 Chat Completions 的服务） |
| 调整提示词 | `agent/prompts.py` |
